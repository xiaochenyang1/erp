# ERP 系统需求设计文档（V1）

**日期**：2026-04-28  
**项目**：`erpServer`  
**技术栈**：`Spring Boot + MySQL + Redis`  
**目标**：构建一套可真实上线试运行的通用 ERP 后端系统

---

## 1. 系统定位

本系统定位为一套面向中大型企业内部运营管理的通用 ERP 后端系统，以 `Web 管理后台` 为唯一一期终端，采用 `Spring Boot + MySQL + Redis` 技术栈，实现采购、销售、库存、财务、审批、报表等核心业务能力。

系统第一期目标不是做成“大而全”的全行业万能平台，而是做成一套可真实上线试运行的企业级 ERP 基础内核，满足单公司、单账套、多仓库场景下的标准化经营管理需求。整体采用模块化单体架构，部署为单实例，但代码结构、缓存策略、权限模型、日志审计、任务处理均按后续可扩展到多实例的标准设计。

系统核心价值在于打通企业运营主链路：

- 商品主数据可管理
- 采购流程可闭环
- 销售流程可闭环
- 库存台账可追溯
- 资金往来可登记
- 凭证账簿可查询
- 审批流可管控
- 报表可支撑经营分析

- 移动端、小程序、APP
- 多实例集群部署
- 复杂 BI 分析平台

### 2.3 一期业务边界原则

- 一期只服务单公司、单账套、多仓库
- 一期只做 Web 管理后台所需后端能力
- 所有库存变化必须通过业务单据或库存调整单触发
- 所有财务往来必须与业务单据建立可追踪关联
- 所有关键单据必须保留状态流转和审计轨迹

## 3. 用户角色与典型业务场景

### 3.1 核心用户角色

- 系统管理员：负责用户、角色、菜单、权限、参数、编号规则、基础字典维护
- 企业管理员：负责公司级基础配置和全局业务查看
- 采购员：发起采购订单、跟踪到货、处理采购退货、维护供应商往来
- 销售员：创建销售订单、跟踪发货、处理销售退货、跟踪客户应收和回款
- 仓库管理员：处理入库、出库、盘点、库存调整，查看台账和预警
- 财务人员：处理收付款、费用登记、科目维护、凭证和账簿查询
- 审批人/主管：对采购、销售、库存、财务关键单据进行审批或驳回
- 管理层：查看经营报表、库存情况、销售采购趋势、应收应付概览

### 3.2 典型业务场景

#### 场景一：采购入库闭环

- 采购员创建采购订单并提交审批
- 审批通过后，仓库管理员根据到货情况执行入库
- 系统支持同一采购订单分批入库
- 入库完成后更新库存台账，并形成应付依据
- 财务人员登记付款，核销应付余额

#### 场景二：销售出库闭环

- 销售员创建销售订单并提交审批
- 审批通过后，仓库管理员根据发货情况执行出库
- 系统支持同一销售订单分批出库
- 出库完成后更新库存台账，并形成应收依据
- 财务人员登记收款，核销应收余额

#### 场景三：库存盘点与调整

- 仓库管理员发起盘点任务
- 录入盘点结果后，系统生成盈亏差异
- 审批通过后执行库存调整
- 系统记录调整前后数量和金额变化，并保留审计轨迹

#### 场景四：财务查询与凭证跟踪

- 财务人员按业务单据查询应收、应付、收款、付款记录
- 系统根据业务事件或财务登记生成对应凭证
- 财务人员可查看总账和明细账
- 管理层可基于财务数据查看基础经营报表

#### 场景五：数据权限控制

- 销售员只能看自己负责或所属范围内的销售数据
- 仓库管理员只能操作被授权仓库的数据
- 部门主管可查看本部门业务数据
- 企业管理员和特定高权限角色可查看全局数据

### 3.3 角色设计原则

- 权限按“功能权限 + 数据权限”分开设计
- 角色只定义能力边界，不直接写死业务逻辑
- 同一个用户可被赋予多个角色
- 高权限角色不等于可以绕过所有业务规则
- 审批权限和操作权限应分离，避免自己提单自己批

## 4. 业务流程总览

### 4.1 采购主流程

采购链路：

`采购订单 -> 审批 -> 分批入库 -> 采购退货（可选）-> 应付形成 -> 付款核销 -> 凭证入账`

核心规则：

- 采购订单是采购业务的源头单据
- 采购订单审批通过后，才允许执行入库
- 同一采购订单支持多次入库，直到全部完成
- 入库后增加库存，并形成应付依据
- 采购退货会冲减库存，并同步冲减应付或形成退款依据
- 付款可分多次登记，并与应付余额关联核销
- 付款完成后更新应付状态，并生成对应财务凭证

### 4.2 销售主流程

销售链路：

`销售订单 -> 审批 -> 分批出库 -> 销售退货（可选）-> 应收形成 -> 收款核销 -> 凭证入账`

核心规则：

- 销售订单是销售业务的源头单据
- 销售订单审批通过后，才允许执行出库
- 同一销售订单支持多次出库，直到全部完成
- 出库后减少库存，并形成应收依据
- 销售退货会回补库存，并同步冲减应收或形成退款依据
- 收款可分多次登记，并与应收余额关联核销
- 收款完成后更新应收状态，并生成对应财务凭证

### 4.3 库存主流程

库存链路：

`采购入库/销售出库/退货/盘点/调整 -> 库存变动 -> 台账记录 -> 报表汇总`

核心规则：

- 库存不能被随意直接改写，必须通过单据或库存调整动作变更
- 每次库存变动都必须记录来源单据、操作人、仓库、商品、数量、金额、时间
- 库存盘点用于发现账实差异，盘点结果不能直接生效，需进入调整流程
- 库存调整必须保留调整原因和审批轨迹
- 库存预警按商品和仓库维度判断，支持最低库存提醒

### 4.4 财务主流程

财务链路：

`业务单据形成往来 -> 收付款/费用登记 -> 凭证生成 -> 总账/明细账查询`

核心规则：

- 采购业务形成应付，销售业务形成应收
- 收款单、付款单用于核销往来余额，可部分核销
- 费用登记独立管理，并可生成对应凭证
- 会计科目、凭证、总账、明细账构成一期轻量财务主线
- 一期不做复杂成本核算、税务申报和结账体系，但预留后续扩展边界

### 4.5 审批主流程

审批链路：

`草稿 -> 提交审批 -> 审批中 -> 通过/驳回 -> 执行/作废`

核心规则：

- 关键业务单据必须审批通过后才能执行后续动作
- 审批流由系统内置，不支持用户自由编排
- 管理员可配置不同单据类型的审批人和审批层级
- 驳回后的单据可修改后再次提交
- 审批动作必须记录审批人、意见、时间和结果

### 4.6 报表主流程

报表链路：

`业务单据/库存流水/往来记录/凭证数据 -> 汇总计算 -> 统计报表`

核心规则：

- 报表以查询统计为主，不直接修改业务数据
- 所有报表必须受数据权限控制
- 报表口径要与业务台账、财务往来、凭证数据一致
- 一期以常规经营报表和对账报表为主，不做复杂 BI 建模

### 4.7 跨流程一致性原则

- 单据状态必须清晰，不能出现“业务做了但状态没变”
- 库存、应收应付、凭证三者必须能追溯到来源单据
- 审批通过只是允许执行，不等于业务自动完成
- 部分入库、部分出库、部分收付款都必须正确累计和结清
- 所有关键变更都必须写入审计日志

## 5. 功能模块设计总览

### 5.1 平台与系统管理模块

职责：

- 提供整套系统的基础运行能力
- 管理用户、角色、菜单、岗位、部门、字典、参数、编号规则、附件、日志

边界：

- 只负责平台能力，不直接承载采购、销售、库存、财务业务规则
- 给业务模块提供通用支撑，不反向依赖具体业务实现

核心子功能：

- 用户与角色管理
- 菜单与按钮权限
- 部门、岗位、员工基础维护
- 字典与系统参数
- 单据编号规则
- 操作日志、登录日志、审计日志

### 5.2 认证与权限模块

职责：

- 负责登录鉴权、功能权限控制、数据权限控制

核心规则：

- 功能权限解决“能不能操作”
- 数据权限解决“能看哪些数据”
- 业务查询必须接入权限规则
- 高权限角色也不能绕过核心业务校验

### 5.3 主数据模块

职责：

- 管理 ERP 各业务域共享的核心基础资料

边界：

- 主数据是全系统共用事实源
- 一期只支持实物商品，不支持服务、套装、BOM

核心子功能：

- 商品档案
- 客户档案
- 供应商档案
- 仓库档案
- 员工基础资料引用

### 5.4 采购管理模块

职责：

- 承担采购业务全流程管理，从采购订单到入库、退货、付款关联

边界：

- 采购模块负责采购业务状态和单据关系
- 实际库存增减由库存模块落账
- 实际应付形成与核销由财务模块承接

核心子功能：

- 采购订单
- 采购入库
- 采购退货
- 采购单据审批状态管理
- 与应付、付款记录的关联查询

### 5.5 销售管理模块

职责：

- 承担销售业务全流程管理，从销售订单到出库、退货、收款关联

边界：

- 销售模块负责销售单据主流程
- 实际库存扣减由库存模块落账
- 实际应收形成与核销由财务模块承接

核心子功能：

- 销售订单
- 销售出库
- 销售退货
- 销售单据审批状态管理
- 与应收、收款记录的关联查询

### 5.6 库存管理模块

职责：

- 负责库存事实账、库存流水、盘点、调整、预警

边界：

- 库存模块是库存真相来源
- 采购和销售不能自己直接改库存，只能通过库存模块完成落账

核心子功能：

- 实时库存
- 库存台账
- 出入库流水
- 库存盘点
- 库存调整
- 库存预警

### 5.7 财务管理模块

职责：

- 负责业务往来、收付款、费用、凭证、账簿的轻量财务能力

边界：

- 一期不做完整财务中台，只做轻量财务闭环
- 财务模块接收采购、销售等业务结果，形成应收应付及凭证数据

核心子功能：

- 应收管理
- 应付管理
- 收款单
- 付款单
- 费用登记
- 会计科目
- 记账凭证
- 总账
- 明细账

### 5.8 审批管理模块

职责：

- 为关键业务单据提供固定审批流能力

边界：

- 审批模块只负责审批状态和审批记录，不直接替业务模块做入库、出库、记账

核心子功能：

- 审批流程定义
- 审批节点配置
- 审批记录
- 驳回与重提
- 待办审批查询

### 5.9 报表中心模块

职责：

- 面向经营分析和业务查询输出标准统计报表

边界：

- 报表模块只读业务和财务结果，不反向修改业务数据
- 报表必须服从数据权限规则

核心子功能：

- 采购统计
- 销售统计
- 库存统计
- 应收应付统计
- 财务查询类报表

### 5.10 通用基础能力模块

职责：

- 提供各业务模块都会用到的横切能力

核心子功能：

- 统一异常处理
- 统一返回结构
- 参数校验
- 幂等控制
- 审计日志
- 业务事件发布
- 缓存封装
- 导入导出能力
- 时间、金额、编号等通用工具

### 5.11 模块协作原则

- 平台模块提供基础能力，业务模块依赖平台
- 主数据是共享底座，采购、销售、库存、财务统一引用
- 采购和销售负责业务单据，库存负责库存事实账，财务负责资金和账务结果
- 审批模块控制流转门禁，报表模块负责结果展示
- 模块之间通过清晰接口协作，避免直接互查互改核心表

## 6. 核心业务对象与数据模型草案

### 6.1 建模原则

- 采用单据头 + 单据明细建模方式
- 采用业务单据与执行结果分离设计
- 采用事实账与统计结果分离设计
- 所有关键对象必须带完整审计字段
- 金额与数量字段统一采用高精度数值类型
- 一期按单公司、单账套运行，但预留 `company_id`、`account_book_id`
- 关键业务数据默认禁物理删除

- `wf_approval_definition`
- `wf_approval_node_definition`
- `wf_approval_instance`
- `wf_approval_task`
- `wf_approval_record`

### 6.9 报表相关数据对象

一期报表中心以查询为主，优先基于以下对象汇总：

- 采购订单、采购入库、采购退货
- 销售订单、销售出库、销售退货
- 库存余额、库存流水
- 应收、应付、收付款
- 凭证、凭证分录

后续如查询压力增大，可补充：

- 日汇总表
- 月汇总表
- 报表快照表

### 6.10 核心对象关系主线

- 商品/客户/供应商/仓库是主数据根对象
- `采购订单 -> 采购入库 -> 库存流水 -> 应付 -> 付款 -> 凭证`
- `销售订单 -> 销售出库 -> 库存流水 -> 应收 -> 收款 -> 凭证`
- `盘点任务 -> 库存调整 -> 库存流水`
- `业务单据 -> 审批实例 -> 审批记录`
- `凭证 -> 分录 -> 总账/明细账查询结果`

### 6.11 一期关键建模约束

- 单据编号必须唯一
- 单据状态、审批状态、执行状态要分开
- 明细行必须保留源单关联关系
- 金额类字段要统一含税/未税口径
- 库存流水必须做到可回放
- 凭证分录必须满足借贷平衡
- 数据权限相关字段要能被快速过滤

## 7. 技术架构与分层设计

### 7.1 总体技术架构

- 核心框架：`Spring Boot`
- 数据库：`MySQL 8`
- 缓存：`Redis`
- 持久层：建议 `MyBatis-Plus` 或 `MyBatis`
- 鉴权：`Spring Security + JWT`
- 接口文档：`OpenAPI / Swagger`
- 参数校验：`Bean Validation`
- 日志体系：`SLF4J + Logback`
- 数据库版本管理：建议 `Flyway`
- 构建工具：`Maven`

运行架构：

`Web 管理后台 -> Spring Boot ERP 后端 -> MySQL + Redis`

### 7.2 模块化单体架构原则

建议按业务域拆分模块：

- `system`
- `auth`
- `masterdata`
- `purchase`
- `sales`
- `inventory`
- `finance`
- `workflow`
- `report`
- `common`

原则：

- 模块之间通过明确服务接口协作
- 不允许一个模块绕过服务层直接改另一个模块的核心表
- 模块边界优先按业务职责划分

### 7.3 分层设计建议

每个业务模块内部建议采用统一分层：

- `controller`
- `application`
- `domain`
- `infrastructure`
- `mapper` / `repository`
- `model`

职责：

- `controller`：参数接收、权限注解、返回封装
- `application`：流程编排、事务边界
- `domain`：核心业务规则和状态流转
- `infrastructure`：数据库、Redis、文件、第三方能力封装

### 7.4 接口设计原则

- 只提供标准 REST 风格接口给 Web 管理后台
- 统一 URL 风格、响应结构、异常码、分页结构、鉴权机制和审计日志
- 查询接口和写入接口分开设计
- 状态流转操作单独建接口，如 `submit`、`approve`、`reject`、`cancel`、`close`

### 7.5 MySQL 设计原则

- 统一主键策略
- 核心编码字段建立唯一索引
- 高频查询字段建立组合索引
- 金额使用高精度定点数
- 状态字段、删除标记、审计字段统一规范
- 大文本、附件、日志与业务主表适当解耦

建议统一审计字段：

- `id`
- `created_by`
- `created_time`
- `updated_by`
- `updated_time`
- `deleted_flag`
- `remark`

### 7.6 Redis 使用策略

Redis 作为辅助设施使用，不作为业务真相来源。第一期建议用于：

- 登录 Token / 会话控制
- 验证码或短期安全数据
- 热点字典与参数缓存
- 权限数据缓存
- 编号生成辅助缓存
- 幂等控制
- 防重复提交
- 审批待办、报表统计等短时缓存

### 7.7 事务与一致性设计

- 单据保存、审批状态变更、库存落账、应收应付生成、凭证生成要明确事务边界
- 一个接口只做一类明确动作，减少超大事务
- 报表汇总、预警刷新、日志归档等非核心同步动作可考虑异步化
- 关键动作要设计幂等和状态校验

### 7.8 安全与权限架构

- 使用 `Spring Security + JWT`
- 密码加密存储
- 登录失败限制
- 关键操作审计
- 敏感接口权限校验
- 数据权限在查询层和业务层双重约束

### 7.9 可扩展性设计

建议预留：

- `company_id`
- `account_book_id`
- 扩展字段或扩展表
- 业务事件机制
- 审批定义与审批实例分离
- 报表汇总能力可扩展

### 7.10 初始化数据库脚本交付策略

第一期数据库初始化建议按以下方式交付：

- `01_schema.sql`：建库建表、主键、字段、默认值
- `02_index.sql`：索引、唯一约束
- `03_init_dict.sql`：字典、参数、编号规则
- `04_init_security.sql`：管理员、角色、菜单、权限
- `05_init_finance.sql`：默认会计科目、基础财务配置
- `06_demo_data.sql`：可选演示数据

建议正式实施时：

- 开发环境：`schema + init data`
- 测试/生产环境：`Flyway` 版本迁移

## 8. 核心非功能需求与质量属性

### 8.1 性能目标

- 常规列表查询接口：95% 请求响应时间控制在 1 秒内
- 常规详情查询接口：95% 请求响应时间控制在 500ms - 1 秒
- 单据保存、提交审批、审核等写操作：正常情况下控制在 2 秒内
- 复杂统计查询：页面查询尽量控制在 3 秒内，大报表导出异步化
- 登录、权限加载、菜单加载：控制在 1 秒内

### 8.2 安全要求

- 使用 `Spring Security + JWT`
- 密码必须加密存储，建议 `BCrypt`
- 登录失败次数限制与临时锁定机制
- 强制接口鉴权
- 关键接口做功能权限校验
- 查询接口做数据权限校验
- 敏感操作写入审计日志

### 8.3 数据一致性要求

- 审批通过前，正式入库和出库动作不得生效
- 库存余额必须由库存流水累计推导和校验
- 应收应付余额必须由来源单据与核销记录共同确定
- 付款、收款、费用、凭证之间必须保留可追溯关系
- 凭证分录必须满足借贷平衡

### 8.4 审计与可追溯要求

必须记录：

- 谁创建单据
- 谁修改单据
- 谁提交审批
- 谁审批通过/驳回
- 谁执行入库/出库/调整/收付款
- 操作时间
- 关键状态变化

必须可追溯：

- `采购订单 -> 采购入库 -> 库存流水 -> 应付 -> 付款 -> 凭证`
- `销售订单 -> 销售出库 -> 库存流水 -> 应收 -> 收款 -> 凭证`
- `盘点任务 -> 库存调整 -> 库存流水`
- `业务单据 -> 审批实例 -> 审批记录`

### 8.5 可用性与恢复能力

- 提供健康检查接口
- 关键配置外置化
- 系统异常时输出清晰错误日志
- MySQL 必须具备定期备份方案
- Redis 缓存丢失后不影响核心业务恢复

建议恢复目标：

- `RPO`：1 天内
- `RTO`：4 小时内

### 8.6 可维护性要求

- 模块边界清晰
- 公共能力统一封装
- 统一异常码、统一返回结构、统一日志规范
- 统一单据状态定义和枚举管理
- 配置与代码分离
- 数据库结构变更必须版本化管理

### 8.7 可测试性要求

- 核心业务规则具备单元测试
- 关键流程具备集成测试
- 关键接口具备接口测试
- 审批、库存、应收应付、凭证生成重点覆盖
- 初始化 SQL 和迁移脚本要可在测试环境自动验证

### 8.8 可观测性要求

- 应用运行日志
- 接口访问日志
- 关键业务操作日志
- 审计日志
- 异常堆栈日志
- 慢查询监控
- 请求耗时、错误率、任务执行结果等基础指标

### 8.9 可扩展性要求

- 模块之间通过清晰接口协作
- 审批定义与审批实例分离
- 关键字段预留多组织、多账套扩展位
- 报表可演进到汇总表或离线统计

### 8.10 运维与交付要求

建议一期交付至少包含：

- 后端源码
- 数据库初始化脚本
- 数据库版本迁移脚本
- 基础配置说明
- 接口文档
- 部署说明
- 默认账号权限说明
- 日志与备份说明

日志与审计：

### 9.2 认证与权限模块

- 支持验证码或登录防刷机制
- 支持登录失败次数限制与锁定

- 数据权限支持按仓库、部门、岗位控制

仓库管理：

## 10. 关键业务规则与约束清单

### 10.1 通用规则

- 所有核心业务单据必须有唯一单号，单号生成不可重复
- 所有核心业务单据必须区分业务状态、审批状态、执行状态
- 已提交审批的单据，除允许修改字段外，不得随意编辑
- 已完成执行的单据原则上不得直接删除，只能作废、关闭或通过反向单据冲销
- 所有关键业务操作必须记录操作人、操作时间、来源单据、变更结果

### 10.2 审批规则

- 需审批单据必须先提交审批，审批通过后才能执行后续动作
- 驳回后的单据可修改后重新提交，但必须保留历史审批记录
- 审批人与制单人原则上隔离，默认不允许自己提单自己审批
- 审批通过表示允许执行，不表示自动完成入库、出库、收付款、记账

### 10.3 采购规则

- 采购订单是采购业务源头，采购入库必须关联采购订单
- 采购入库数量不得超过订单剩余可入库数量
- 支持分批入库，系统累计已入库数量并自动判断是否完成
- 采购退货必须关联已入库记录，退货数量不得超过可退数量
- 采购入库成功后形成库存增加事实，并生成应付依据
- 采购付款可分多次登记，累计付款金额不得超过应付金额

### 10.4 销售规则

- 销售订单是销售业务源头，销售出库必须关联销售订单
- 销售出库数量不得超过订单剩余可出库数量
- 支持分批出库，系统累计已出库数量并自动判断是否完成
- 销售退货必须关联已出库记录，退货数量不得超过可退数量
- 销售出库成功后形成库存减少事实，并生成应收依据
- 销售收款可分多次登记，累计收款金额不得超过应收金额
- 第一期开启不允许负库存规则

### 10.5 库存规则

- 库存余额必须由库存流水驱动变更
- 所有入库、出库、退货、调整、盘点差异处理都必须生成库存流水
- 库存流水必须记录来源单据类型、来源单据号、仓库、商品、数量、金额、方向
- 盘点结果不能直接覆盖库存，必须通过库存调整单生效
- 库存调整必须填写原因

### 10.6 财务规则

- 应收必须来源于销售业务，应付必须来源于采购业务或明确财务登记动作
- 收款、付款必须支持部分核销，并保留核销明细
- 应收应付的剩余金额必须由原始金额减累计核销金额得出
- 凭证分录必须满足借贷平衡，不平衡不得保存为有效凭证
- 凭证必须可追溯来源业务单据、收付款单或费用单

### 10.7 主数据规则

- 商品、客户、供应商、仓库采用启停管理，原则上不做物理删除
- 已被业务单据引用的主数据，不允许删除
- 商品编码、客户编码、供应商编码、仓库编码必须唯一
- 停用状态的主数据不得参与新建业务单据

### 10.8 权限与数据隔离规则

- 功能权限和数据权限必须同时生效
- 数据权限至少按仓库、部门、岗位控制，并支持负责人或创建人范围补充
- 列表、详情、导出接口都必须应用数据权限
- 高权限用户也必须留下审计记录

### 10.9 并发与幂等规则

- 单据提交、审批、入库、出库、收付款、生成凭证等关键动作必须防重复提交
- 同一张单据同一时刻只能有一个有效执行路径
- 关键状态变更应做前置状态校验，必要时使用乐观锁版本号
- 编号生成必须保证并发下唯一

### 10.10 作废、关闭与冲销规则

- 草稿单可删除或作废
- 已审批或已执行单据原则上不可直接删除
- 已发生库存或财务影响的单据，如需纠正，应通过退货、红冲、调整等反向业务处理
- 作废动作必须记录原因和操作人

### 10.11 金额、税额与口径规则

- 金额字段统一使用高精度定点数
- 金额、税额、含税金额、未税金额口径必须统一定义
- 第一期开启单币种人民币，不做汇率换算
- 税率采用基础配置，不做复杂税务申报逻辑

### 10.12 报表与追溯规则

- 报表属于统计结果，不得反向修改业务数据
- 报表必须能追溯到来源业务单据、库存流水或凭证分录
- 数据权限必须作用到报表查询和导出

### 10.13 一期必须坚持的底线

- 不允许负库存
- 不允许未审批先执行关键业务
- 不允许无来源改库存
- 不允许应收应付与收付款脱节
- 不允许凭证借贷不平
- 不允许靠前端控制数据权限

## 11. 接口分层与 API 设计原则

### 11.1 API 总体风格

一期接口采用 RESTful 风格 + 明确动作接口组合方式。

示例：

- `GET /api/products`
- `GET /api/products/{id}`
- `POST /api/products`
- `PUT /api/products/{id}`
- `POST /api/products/{id}/enable`
- `POST /api/products/{id}/disable`

- `GET /api/purchase-orders`
- `GET /api/purchase-orders/{id}`
- `POST /api/purchase-orders`
- `PUT /api/purchase-orders/{id}`
- `POST /api/purchase-orders/{id}/submit`
- `POST /api/purchase-orders/{id}/approve`
- `POST /api/purchase-orders/{id}/reject`
- `POST /api/purchase-orders/{id}/cancel`
- `POST /api/purchase-orders/{id}/close`

### 11.2 接口分层原则

- 基础资料接口
- 业务单据接口
- 流程动作接口
- 查询统计接口
- 系统管理接口
- 导入导出接口

### 11.3 统一请求与响应规范

统一响应结构：

```json
{
  "code": "0",
  "message": "success",
  "data": {},
  "traceId": "xxxxxx"
}
```

分页响应结构：

```json
{
  "code": "0",
  "message": "success",
  "data": {
    "pageNo": 1,
    "pageSize": 20,
    "total": 120,
    "records": []
  },
  "traceId": "xxxxxx"
}
```

### 11.4 查询接口设计原则

- 列表查询默认分页
- 支持按关键字段、时间范围、状态过滤
- 支持按仓库、部门、负责人等数据权限相关维度过滤
- 导出接口不得直接复用无限制分页查询逻辑

### 11.5 单据详情接口设计原则

详情结构建议至少包含：

- 单据头信息
- 单据明细列表
- 审批信息
- 执行进度信息
- 关联单据摘要
- 审计摘要

示例：

```json
{
  "code": "0",
  "message": "success",
  "data": {
    "header": {},
    "lines": [],
    "approvalInfo": {},
    "executionInfo": {},
    "relatedDocs": [],
    "auditSummary": {}
  }
}
```

### 11.6 写接口设计原则

- 新增和修改接口只负责保存数据
- 提交审批使用独立接口
- 审批通过/驳回使用独立接口
- 入库、出库、盘点生效、调整生效使用独立接口
- 收付款登记使用独立接口
- 凭证生成使用独立接口或明确业务事件驱动

### 11.7 状态流转接口设计原则

必须校验：

- 当前单据状态是否合法
- 当前审批状态是否合法
- 当前用户是否有操作权限
- 当前数据范围是否允许操作
- 当前单据是否已被执行或关闭
- 是否存在重复提交风险

### 11.8 鉴权与权限控制规范

- 未登录不得访问业务接口
- 需要功能权限的接口必须声明权限标识
- 需要数据权限的查询必须强制拼接权限过滤
- 涉及敏感业务操作的接口必须记录审计日志

### 11.9 幂等与防重复提交规范

重点场景：

- 提交审批
- 审批通过/驳回
- 采购入库
- 销售出库
- 收款登记
- 付款登记
- 凭证生成
- 导入处理

建议策略：

- 前端提交幂等标识
- 后端结合 Redis 做短期防重
- 关键动作叠加数据库状态校验

### 11.10 导入导出接口原则

导入：

- 一期仅开放主数据类导入
- 提供模板下载
- 导入前校验必填项、编码唯一性、字典合法性
- 导入结果返回成功/失败明细

导出：

- 普通列表导出可同步处理
- 大报表导出建议异步任务化
- 导出内容必须服从当前用户数据权限
- 导出操作必须记录日志

### 11.11 错误码与异常处理原则

建议错误分类：

- 参数错误
- 权限不足
- 数据不存在
- 状态非法
- 业务规则冲突
- 并发冲突
- 系统异常

### 11.12 API 文档与版本管理原则

- 使用 `OpenAPI / Swagger`
- 每个接口具备清晰描述、参数说明、权限要求、返回示例
- 关键业务动作接口要标明前置条件
- 第一阶段内部接口可不做复杂版本号管理，但必须保持兼容性意识

### 11.13 一期接口设计底线

- 不允许万能接口混做多个动作
- 不允许前端决定权限边界
- 不允许查询接口绕开数据权限
- 不允许关键写操作没有幂等保护
- 不允许导出绕开权限控制

## 12. 数据库设计与初始化脚本规划

- 单据头与明细通过 `header_id` 逻辑关联
- 高频跨模块关联以逻辑外键 + 索引 + 应用层校验为主

### 12.6 索引设计原则

- 所有编码、业务单号建立唯一索引
- 所有明细表的头表关联字段建立普通索引
- 状态字段与时间字段组合查询考虑联合索引
- 数据权限相关字段优先建索引，如 `warehouse_id`、`dept_id`、`owner_user_id`
- `inv_stock_balance` 对 `warehouse_id + product_id` 建唯一索引
- `inv_stock_txn` 对 `warehouse_id + product_id + created_time` 建联合索引

### 12.7 金额与数量字段规范

- 数量建议使用 `decimal(18,6)`
- 单价建议使用 `decimal(18,6)`
- 金额建议使用 `decimal(18,2)` 或 `decimal(18,4)`
- 税率建议使用 `decimal(8,4)`
- 统一字段命名：`qty`、`price`、`amount`、`tax_rate`、`tax_amount`

- 生产环境：执行结构脚本 + 安全初始化脚本，初始密码和敏感参数必须人工确认

- 不允许状态字段命名混乱
- 不允许初始化脚本只建表不带基础权限和参数

- 把当前空仓库拉成能承载企业级开发的后端骨架

范围：

- 统一项目结构
- 基础依赖与配置
- MySQL、Redis、Swagger、Security 接入
- 统一返回结构、异常体系、日志体系

- 字典、参数、编号规则
- 商品、客户、供应商、仓库

- 阶段 0：产出数据库脚本总体目录和基础框架
- 阶段 1：补齐平台、权限、主数据初始化

- 阶段 3：补齐财务基础科目与凭证相关初始化
- 阶段 4：补齐演示数据和测试数据脚本

### 13.4 第一阶段推荐实施顺序

1. 先重构当前空项目为正式 Spring Boot 工程骨架
2. 建立统一分层、统一依赖、统一配置、统一异常与返回结构
3. 先落数据库基础脚本和 Flyway 迁移机制
4. 再做认证鉴权、角色权限、数据权限
5. 然后做主数据模块
6. 再做采购、销售、库存主链路
7. 接着做财务与审批联动
8. 最后做报表、性能优化、上线准备

### 13.5 实施阶段的质量门槛

- 代码可编译、可启动
- 数据库脚本可独立初始化
- 核心接口可联调
- 核心测试可运行
- 文档与接口说明同步更新
- 关键日志和审计链路可验证

### 13.6 不建议的错误推进方式

- 不要先把所有表一口气拍满，再去补业务逻辑
- 不要先写前端页面，再倒逼后端瞎凑接口
- 不要把采购、销售、库存、财务混在一个大 `service` 里乱写
- 不要等功能都写差不多了才补权限、日志、初始化脚本
- 不要把审批、库存、财务规则写在前端交互里

### 14.1 一期验收标准

- 用户、角色、菜单、数据权限可正常使用
- 商品、客户、供应商、仓库主数据可维护
- 采购订单到入库到付款链路跑通
- 销售订单到出库到收款链路跑通
- 库存余额与流水可核对
- 应收应付与核销关系清晰
- 凭证、总账、明细账可查询
- 固定审批流可配置并生效
- 核心报表可查询和导出
- 初始化脚本可在空库独立执行成功
- 系统可部署并完成试运行环境启动

### 14.2 当前设计结论

- 做通用 ERP
- 技术栈锁定 `Spring Boot + MySQL + Redis`
- 架构采用模块化单体
- 目标是单公司、单账套、多仓库
- 一期只做 Web 管理后台后端
- 覆盖平台、权限、主数据、采购、销售、库存、轻量财务、固定审批流、基础报表
- 支持分批入库、分批出库、部分收付款、退货
- 不做多组织、多币种、批次/效期/序列号、移动端和外部集成
- 数据权限按仓库、部门、岗位控制
- 交付目标是可真实上线试运行
