# B1 数据范围运营加固设计

**日期**：2026-08-25  
**状态**：已完成 B1 运营验收；B8 看板 scope 统一待后续  
**目标**：让受限账号在单据列表、详情、导出、报表和业务追踪中的可见数据保持同一套数据范围语义，并为越权写入建立回归门禁。

## 1. 背景

系统已经具备 `ALL / DEPT / POST / WAREHOUSE / SELF` 数据范围模型、角色/用户配置界面、登录态快照以及采购、销售、库存和订单报表的基础过滤。现阶段的风险不在于缺少模型，而在于不同只读入口可能只做了公司/账套隔离，未复用同一套数据范围判定。

本轮只做运营加固，不改变数据范围类型、角色与用户并集规则，也不新增业务模块。

## 2. MVP 范围

### 2.1 必须覆盖

- 采购订单、采购入库、采购退货、销售订单、销售出库、销售退货：列表与详情继续使用统一 `DataScopeService` 判定。
- 采购订单、销售订单、库存余额、库存流水：导出/报表查询必须与页面列表使用同一 scope wrapper。
- 业务追踪：先对订单、出入库和库存流水做数据范围过滤；受限账号的财务、日志、异常工单结果只能从已可见业务号关联产生，不能通过直接输入隐藏的财务号绕过范围。
- 越权详情和写操作：返回 `403` 或统一的业务拒绝异常，且在拒绝前不发生明细加载、状态更新或下游过账。
- 非管理员双账号端到端 smoke：一个账号授权单仓/SELF，另一个账号保留 `ALL` 作为对照。

### 2.2 明确不做

- 不改变 `ALL / DEPT / POST / WAREHOUSE / SELF` 的业务语义。
- 不把完整数据范围写入 JWT，不新增权限版本号或强制踢出机制。
- 不在本轮重构全部报表 SQL；对于缺少稳定来源关联的历史财务/日志数据，采用默认拒绝和已知业务号关联策略。
- 不把前端过滤当作安全边界。

## 3. 统一判定规则

1. 先做公司和账套隔离，再做数据范围判定。
2. 多个范围采用并集；命中 `ALL` 直接放行。
3. 列表和导出必须在数据库查询条件中下推，禁止先分页后内存过滤。
4. 详情先查实体，再调用统一断言；断言失败时不得加载供应商、客户、明细或关联单据。
5. 写操作必须先通过详情守卫，再执行状态校验和任何持久化/过账副作用。

## 4. 验收标准

- 受限账号的页面列表、CSV、订单报表对同一筛选条件返回相同的业务单据集合。
- `SELF` 账号看不到他人创建的采购/销售单据；`WAREHOUSE` 账号看不到未授权仓库的库存、出入库和退货数据。
- 受限账号直接访问他人详情、过账、审批、作废、编辑接口时返回 `403` 或明确拒绝，数据库状态和下游调用保持不变。
- 业务追踪输入隐藏财务编号、日志编号或异常工单编号时不得返回隐藏对象；输入可见订单号时，关联链路只能包含可见对象。
- 自动化测试覆盖：scope wrapper、详情守卫短路、导出复用、报表复用、业务追踪关联过滤；API smoke 覆盖双账号、六类核心单据列表/详情/导出、订单/库存报表、库存余额/流水、非授权仓详情和越权写零副作用。

## 5. 非目标与后续

经营看板的金额聚合和 TOP SKU 需要额外的来源关联/仓库参数，不能只靠前端隐藏卡片完成。本轮先记录为矩阵中的待补项；下一步 B8 在设计指标 SQL 时必须直接复用本轮数据范围策略。
