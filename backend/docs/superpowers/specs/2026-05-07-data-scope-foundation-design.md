# ERP 数据权限底座设计文档

**日期**：2026-05-07  
**项目**：`erpServer`  
**技术栈**：`Spring Boot + MyBatis-Plus + Spring Security + JWT + Flyway`  
**主题**：采购查询数据权限底座

---

## 1. 设计目标

本轮目标是在现有 `功能权限` 已闭环的基础上，补齐最小可用的 `数据权限` 底座，先让采购相关查询接口真正具备“你有权限进系统，不等于你能看全部数据”的控制能力。

本轮完成后，系统需要具备以下能力：

- 支持通过角色和用户两条来源配置数据范围
- 支持 `ALL / DEPT / POST / WAREHOUSE / SELF` 五种数据范围
- 登录后可在认证上下文中拿到数据范围快照，而不是每次查询现算一遍
- 采购订单、采购入库、采购退货的 `列表` 和 `详情` 查询统一受数据权限约束
- 列表和详情共享同一套判定语义，不能出现“列表拦了，详情没拦”的低级漏洞

本轮重点是把权限边界和聚合逻辑写扎实，不追求把全系统所有模块一口气全接进去。

## 2. 范围与边界

### 2.1 本轮纳入范围

- 新增角色数据范围表
- 新增用户数据范围表
- 登录态数据范围快照聚合
- 采购订单查询数据权限接入
- 采购入库查询数据权限接入
- 采购退货查询数据权限接入
- 自动化测试覆盖聚合、列表过滤、详情越权拦截

### 2.2 本轮明确不做

- 不扩到商品、仓库、客户、供应商等主数据查询
- 不扩到销售、财务、报表、库存其他业务模块
- 不做前端参与的数据权限判断
- 不做导出接口的数据权限控制实现，仅要求设计上与列表/详情共享同一套判定逻辑
- 不引入复杂多租户隔离、公司级或账套级动态路由

### 2.3 边界原则

- 这轮只做 `采购相关查询` 的数据权限，不改采购写入流程语义
- 详情接口也算查询，必须与列表同样受控
- 先保证规则正确和可测试，再考虑后续在更多模块复用

## 3. 权限语义设计

### 3.1 支持的数据范围类型

- `ALL`：可见全部目标数据
- `DEPT`：可见与当前登录用户所属部门匹配的数据
- `POST`：可见与当前登录用户所属岗位匹配的数据
- `WAREHOUSE`：可见数据范围配置中显式授权仓库的数据
- `SELF`：只可见 `created_by = 当前用户` 的数据

### 3.2 范围口径

为避免第一版把规则做成一锅浆糊，本轮口径固定如下：

- `DEPT`：直接使用当前登录用户自身的 `dept_id`
- `POST`：直接使用当前登录用户自身的 `post_id`
- `WAREHOUSE`：必须通过数据范围表显式配置 `warehouse_id`
- `SELF`：按 `created_by = 当前登录用户 id` 判定

这里不引入“负责人”“归属人”“业务员”等额外口径，避免第一版语义飘掉。

### 3.3 合并规则

用户最终数据范围采用 `并集` 语义：

- 用户直接配置的数据范围参与合并
- 用户所属角色继承的数据范围参与合并
- 只要命中任一范围即可访问
- 一旦命中 `ALL`，则直接视为全局可见

不采用“用户覆盖角色”或“只认角色”模型，因为当前阶段更需要稳定和可理解，而不是做一套后续运维容易配错的优先级迷宫。

## 4. 数据模型设计

### 4.1 新增表：`sys_role_data_scope`

用途：给角色配置数据权限范围。

建议字段：

- `id`
- `role_id`
- `scope_type`
- `warehouse_id`
- `created_by`
- `created_time`

关键约束：

- `scope_type` 仅允许 `ALL / DEPT / POST / WAREHOUSE / SELF`
- `WAREHOUSE` 类型必须携带 `warehouse_id`
- 非 `WAREHOUSE` 类型必须为空 `warehouse_id`
- 建议唯一索引：`(role_id, scope_type, warehouse_id)`

### 4.2 新增表：`sys_user_data_scope`

用途：给用户补充或追加数据权限范围。

建议字段：

- `id`
- `user_id`
- `scope_type`
- `warehouse_id`
- `created_by`
- `created_time`

关键约束：

- `scope_type` 仅允许 `ALL / DEPT / POST / WAREHOUSE / SELF`
- `WAREHOUSE` 类型必须携带 `warehouse_id`
- 非 `WAREHOUSE` 类型必须为空 `warehouse_id`
- 建议唯一索引：`(user_id, scope_type, warehouse_id)`

### 4.3 初始化数据

本轮迁移脚本需要包含最小幂等初始化数据：

- 给现有 `SUPER_ADMIN` 或管理员角色补一条 `ALL`

这么做的目的很朴素：避免数据权限底座上线后先把管理员自己锁死，整成“功能做出来了，但没人能查全量数据”的闹剧。

## 5. 认证上下文设计

### 5.1 `ErpPrincipal` 扩展

当前 `ErpPrincipal` 已承载登录用户基础信息和功能权限，本轮追加：

- `Long deptId`
- `Long postId`
- `DataScopeSnapshot dataScopeSnapshot`

该快照用于表达登录态的最终数据权限结果，而不是原始数据库记录。

### 5.2 `DataScopeSnapshot` 结构

建议最小结构：

- `boolean hasAllScope`
- `boolean deptScoped`
- `boolean postScoped`
- `boolean selfScoped`
- `Set<Long> warehouseIds`

设计原则：

- 保留的是“判定结果”，不是一堆零散实体
- 快照必须不可变，避免运行时被意外修改
- 快照必须支持后续复用于销售、库存、报表模块

### 5.3 快照生成时机

快照在登录认证装载用户时生成：

- `DatabaseUserDetailsService` 负责装载用户
- `DataScopeService` 负责聚合角色范围和用户范围
- 聚合完成后塞入 `ErpPrincipal`

同时需要把当前登录用户自身的 `dept_id`、`post_id` 一并装入 `ErpPrincipal`，因为 `DEPT / POST` 范围判定必须依赖当前用户自身所属部门和岗位，而不能只靠布尔标志瞎猜。

不建议在每个 service 查询时重新拼装数据范围，一是性能浪费，二是容易出现某个模块判定口径偷偷跑偏。

### 5.4 登录返回与 JWT 边界

本轮允许在登录响应中返回一个最小数据范围摘要，供前端展示或调试使用，但服务端权限判定绝不依赖前端回传任何数据范围信息。

JWT 保持最小载荷：

- 不把完整数据权限快照写入 token
- 仍然只通过 `userId` 回源装载最新 `ErpPrincipal`

这样可以避免“权限配置已改，但旧 token 里还带着陈旧数据范围”的同步问题。本轮接受“重新登录后拿到最新数据范围”的一致性模型，不在当前阶段引入权限版本号或 token 强制失效机制。

## 6. 服务层接入设计

### 6.1 接入原则

本轮采用 `Service 中心化数据权限` 方案：

- 数据权限语义集中在 `DataScopeService`
- 采购模块 service 调用统一的数据权限判定能力
- 不走 AOP 自动注入
- 不在每个 mapper 里各自发明一套 SQL 方言

### 6.2 建议新增能力

新增 `DataScopeService`，提供最小职责：

- 聚合角色和用户数据范围，生成 `DataScopeSnapshot`
- 为采购订单、采购入库、采购退货列表查询拼装统一的数据权限条件
- 为采购订单、采购入库、采购退货详情查询提供统一断言方法，越权时直接抛出明确异常

建议按“列表条件下推 + 详情断言兜底”的模式提供两类能力：

- `apply...Scope(...)`
  作用：把数据权限条件下推到列表查询 wrapper，保证分页总数、页大小、翻页结果都正确
- `assertCanView...(entity, currentUser, snapshot)`
  作用：详情先查实体，再做统一越权断言

### 6.3 采购订单查询接入

接入位置：

- `PurchaseOrderService.list`
- `PurchaseOrderService.getById`

判定建议：

- `SELF`：按 `created_by`
- `DEPT`：按订单创建人所属部门匹配
- `POST`：按订单创建人所属岗位匹配
- `WAREHOUSE`：本轮对采购订单查询不产生任何额外可见性，不做基于后续入库链路的仓库反推
- `ALL`：直接放行

这里要明确一点：采购订单天然不像入库和退货那样直接带 `warehouse_id`，所以第一版不要为了凑齐所有 SQL 下推而硬写错规则。`WAREHOUSE` 单独存在时，不会让采购订单获得额外可见性；如果用户只配置了 `WAREHOUSE`，那他对采购订单列表就是空结果，对详情就是越权。

列表实现原则：

- 尽量下推到查询条件，不采用“先查一页再内存过滤”的分页歪招
- `DEPT / POST` 第一版允许先查出当前部门或岗位下的活跃用户 id 集合，再拼 `created_by in (...)`
- `SELF` 直接按 `created_by = 当前用户 id`
- 多范围采用并集语义，即 `OR` 组合

### 6.4 采购入库查询接入

接入位置：

- `PurchaseReceiptService.list`
- `PurchaseReceiptService.getById`

判定建议：

- `WAREHOUSE`：直接按 `warehouse_id in (...)`
- `SELF`：按 `created_by`
- `DEPT/POST`：基于创建人所属部门/岗位判断
- `ALL`：直接放行

采购入库单自带 `warehouse_id`，因此这一块的仓库权限可以稳定落地。

### 6.5 采购退货查询接入

接入位置：

- `PurchaseReturnService.list`
- `PurchaseReturnService.getById`

判定建议：

- `WAREHOUSE`：直接按 `warehouse_id in (...)`
- `SELF`：按 `created_by`
- `DEPT/POST`：基于创建人所属部门/岗位判断
- `ALL`：直接放行

采购退货单同样自带 `warehouse_id`，可沿用采购入库的处理模式。

### 6.6 详情越权拦截

详情接口统一原则：

- 先按 `id` 查出实体
- 再走统一 `assertCanAccess(...)`
- 越权时抛出 `AccessDeniedException`

不能因为详情接口通常“只查一条”就偷懒不校验，否则列表过滤就成了给领导演戏。

### 6.7 默认无范围行为

如果某普通用户既没有用户级数据范围，也没有从角色继承到任何数据范围，本轮默认拒绝：

- 列表接口返回空结果
- 详情接口返回 `403`

不做“默认 SELF”或“默认 DEPT”的隐式兜底，避免权限配置缺失时悄悄放宽边界。

## 7. 错误处理与返回语义

- 查询对象不存在：保持现有 `不存在` 语义
- 查询对象存在但无数据权限：返回 `403`

实现建议：

- 详情越权时抛 `AccessDeniedException`
- 复用现有全局异常处理，把数据权限越权统一收口成 `403`
- 列表接口无权限不抛错，直接返回空列表

本轮必须保证：

- 列表接口看不到不该看的数据
- 详情接口不能通过枚举 ID 越权读取

## 8. 测试策略

### 8.1 聚合测试

需要覆盖：

- 角色 `ALL` 直接全量可见
- 用户 `ALL` 直接全量可见
- 用户和角色范围按并集合并
- 仓库范围可累加多个 `warehouse_id`
- `DEPT / POST / SELF` 标志位正确装载
- 无任何范围配置时，快照结果按“默认拒绝”处理

### 8.2 采购订单权限测试

需要覆盖：

- 全局权限用户可查全部订单
- `SELF` 用户只能查自己创建订单
- `DEPT` 用户只能查本部门范围订单
- `POST` 用户只能查本岗位范围订单
- 只有 `WAREHOUSE` 范围的用户对订单列表为空
- 只有 `WAREHOUSE` 范围的用户访问订单详情返回 `403`
- 越权详情被拦截并返回 `403`

### 8.3 采购入库权限测试

需要覆盖：

- `WAREHOUSE` 用户只能看授权仓库入库单
- `SELF` 用户只能看自己创建入库单
- `DEPT / POST` 用户只能看本部门/本岗位创建的入库单
- 越权详情被拦截并返回 `403`

### 8.4 采购退货权限测试

需要覆盖：

- `WAREHOUSE` 用户只能看授权仓库退货单
- `SELF` 用户只能看自己创建退货单
- `DEPT / POST` 用户只能看本部门/本岗位创建的退货单
- 越权详情被拦截并返回 `403`

### 8.5 回归要求

完成本轮后必须执行至少以下检查：

```bash
mvn "-Dmaven.repo.local=E:/tuowei/python/erpServer/.m2/repository" test
```

期望：

- 数据权限新增测试通过
- 采购既有测试不被打崩
- 认证登录链路保持可用

## 9. 验收标准

满足以下条件视为本轮完成：

- 登录态可携带数据权限快照
- 采购订单、采购入库、采购退货列表查询受数据权限过滤
- 同三类单据的详情查询也受数据权限控制
- `ALL / DEPT / POST / WAREHOUSE / SELF` 五种范围可按设计语义工作
- 用户范围与角色范围按并集合并
- 管理员默认具备 `ALL`
- 自动化测试覆盖聚合、列表、详情越权核心场景

## 10. 非目标

本轮明确不做：

- 主数据查询数据权限
- 销售、财务、报表模块数据权限
- 前端展示数据范围配置页面
- 数据权限导出能力
- 多公司、多账套隔离
- 负责人、归属人等额外业务口径

先把采购查询的权限底座做稳，再往外扩，不然最后就会变成一套谁都不敢改、谁改都怕炸的权限面条。
